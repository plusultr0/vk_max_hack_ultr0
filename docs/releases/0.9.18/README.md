# MAX Regulatory Control · 0.9.18

Проверка требований к малому интернет-магазину внутри MAX. Пользователь рассказывает о бизнесе, получает подходящие требования, отвечает на уточняющие вопросы и отмечает готовность документов и действий.

Эта версия продолжает фактический source-state **0.9.16** из handoff 28.09.2026, не пересобирая проект заново и не меняя рабочий `.env`. Архитектура, 37 персонализируемых требований, чат-бот 0.9.15 и исправления regulatory feed 0.9.16 сохранены. 0.9.17 закрывает последний невыполненный UX-запрос: упрощает «Мой бизнес», переименовывает пользовательский раздел с результатами в «Требования», очищает карточки от лишних пояснений/нумерации, форматирует денежный ввод и делает НДС-действия конкретными по дате. **0.9.18** дополнительно убирает из всех карточек дублирующий блок «Ваши ответы, которые повлияли на результат» со списком введённых значений.

**Статус проверки:** в среде подготовки прошли **189/189** offline core/UX/ingestion проверок, chatbot offline gate **9/9**, syntax gate для **102 TS/TSX файлов** и повторный Chromium CSS/layout gate **80/80** на 320/375/768/1024/1440 px. `.env` сохранён без изменений. Полный workspace typecheck/Vitest/Vite build и Docker integration/live не заявляются как пройденные: локальная установка npm dependencies снова не завершилась в доступной среде, Docker CLI отсутствует. Последняя подтверждённая live-версия остаётся 0.9.14; 0.9.15–0.9.18 нужно развернуть на существующем стенде с сохранением production `.env`. Подробности: `TEST_REPORT.md`, `CHANGELOG_0.9.18.md`, `CHANGELOG_0.9.17.md`, `BOT_SCENARIOS_0.9.15.md`.

## 1. Что увидит пользователь

В навигации три раздела: **«Требования»**, **«Изменения»**, **«Мой бизнес»**. На мобильном они остаются одной строкой в нижней навигации; отдельные технические разделы пользователю не показываются.

**Требования.** Сначала показывает то, что требует внимания. Карточка отвечает на три вопроса: что за требование, почему получен такой результат и что делать дальше. После ответа открытая карточка остаётся на экране, даже если результат стал «По вашим ответам — не относится».

**Изменения.** Лента новых и будущих требований с персональным отбором. Фильтры сформулированы обычным языком: «Могут относиться к моему бизнесу», «Добавлены в сервис за последние 90 дней», «Начнут действовать позже».

**Мой бизнес.** Восемь первичных вопросов идут одной последовательностью без дополнительных групп и второго progress-блока. Между вопросами используются обычные разделители с отступом. Для географии можно выбрать «По всей России», «Россия и СНГ» или указать конкретный регион/другой охват. Для УСН текущий onboarding не дробит «Доходы» и «Доходы минус расходы», потому что ни одно из 37 текущих правил не использует объект УСН как условие применимости. В каждом вопросе остаётся явный вариант «Не знаю».

Визуальная система остаётся светлой: тёплый фон, почти чёрный текст, винный акцент, Manrope для интерфейса и Oswald для крупных заголовков. Карточки и формы используют тонкие линии вместо большого количества скруглений и теней. Основная задача редизайна — быстрее считывать статус, следующий шаг и объяснение, а не добавлять декоративные элементы.

В разделе «Требования» находится список **«Документы и важные настройки»**. Для каждого пункта пользователь отмечает понятный результат: документ готов, настройка настроена или действие выполнено; при проблеме выбирает «Нужно подготовить / настроить / выполнить», а при сомнении — «Не знаю». Основание, дата и версия сохраняются. Изменившиеся требования или значимые ответы требуют повторной проверки отметки.

Отдельный checklist документов/настроек по-прежнему содержит 12 базовых шаблонов и динамически дополняется action-пунктами опубликованных правил. Это **не 12 обязательных документов для каждой компании**. Количество зависит от применимости; загружать документы не нужно, их содержание приложение не проверяет. Для применимой нормы карточка теперь отдельно показывает «Что нужно сделать», прогресс обязательных шагов и self-report «Требования выполнены / Требования ещё не выполнены». Этот статус вычисляется из существующих action items и означает только отметку пользователя, а не автоматическое юридическое заключение.

## 2. Первый запуск / обновление

Требуются Docker с Compose и доступ к реестрам образов/npm при первой сборке.

```powershell
cd "путь\к\проекту"
docker compose up -d --build
```

Команда запускает PostgreSQL, миграции, seed, API, web, bot и worker. Уже имеющийся `.env` не заменять `.env.example`. При переносе в новую директорию сохраняйте прежнее имя Compose-проекта, если нужно использовать прежний volume: имя каталога влияет на выбор проекта и базы. Не удаляйте рабочий volume.

Начиная с 0.9.12 healthcheck PostgreSQL выполняет `SELECT 1` в целевой базе. Это исправляет первый запуск на чистом volume, когда `pg_isready` мог вернуть успех до завершения `CREATE DATABASE`, из-за чего `migrate` стартовал слишком рано.

Перед обновлением существующей базы сделайте резервную копию обычным для вашей инфраструктуры способом. Миграция `012_business_checks.sql` добавляет новую таблицу и защиту истории, не удаляет старые профили/правила/действия. Миграции и обновление на реальной базе в среде подготовки не запускались.

Остановка и повторный запуск:

```powershell
docker compose down
docker compose up -d
docker compose logs --tail 100 api worker
```

Для обычного обновления **не использовать `down -v`**.

Адреса локальной разработки:

| Компонент | Адрес / порт |
|---|---|
| Mini-app | `http://localhost:5173` |
| Административный review | `http://localhost:5173/review` |
| API | `http://localhost:3000` |
| API health | `http://localhost:3000/health` |
| Bot health | `http://localhost:3001/health` |
| PostgreSQL | `5432`, настройки из Compose |

По умолчанию frontend обращается к API через тот же origin; Vite проксирует запросы в `API_PROXY_TARGET`. Явно заданный `VITE_API_URL` имеет приоритет. В HTTPS-развёртывании нельзя оставлять адрес API, доступный только на localhost разработчика.

## 3. Полная проверка без рабочей БД и ключей

Из корня в Windows PowerShell:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\acceptance.ps1
```

Либо непосредственно:

```powershell
docker compose --env-file .env.test.example -p max-regcontrol-tests -f compose.test.yaml up --build --abort-on-container-exit --exit-code-from tests
docker compose --env-file .env.test.example -p max-regcontrol-tests -f compose.test.yaml down
```

Это отдельный Compose-проект: PostgreSQL во временной памяти, публичных портов нет, рабочий `.env` не подключается, реальные ключи не используются. После сборки внутренняя сеть тестовых контейнеров не даёт доступа к внешним сервисам.

Выполняются backend typecheck, существующие Vitest-тесты, Vite production build, 189 дополнительных offline-проверок и цепочка PostgreSQL integration, включая новый `usability.integration.ts`. Код завершения 0 означает прохождение именно этого набора. PowerShell сохраняет лог в `test-results/acceptance.log`. Тестовые данные синтетические; этот запуск не подтверждает интеграцию с реальным MAX или GigaChat.

До успешного выполнения этой команды сборку следует считать обновлённой разработческой версией, а не проверенным релизом.

## 4. Проверка без Docker

Требуется Node.js 22, npm, доступ к npm registry, PostgreSQL для интеграционных тестов. Для PDF с текстовым слоем нужен `pdftotext` (Poppler; в Docker добавлен).

```powershell
npm ci
npm run check
npm run check:syntax
```

`check:syntax` проверяет только синтаксис, не заменяет `check`.

```powershell
npm run test:core
```

Этот набор исполняет реальную логику 17 модулей после транспиляции TypeScript. Он не подменяет React, Zod или PostgreSQL. В нём нет теста «имитированная БД работает».

Для выделенной тестовой БД:

```powershell
$env:ALLOW_INTEGRATION_TESTS="true"
$env:DATABASE_URL="postgresql://test_user:test_password@localhost:5432/test_db"
npm run test:integration
```

Не направляйте эту переменную на рабочую БД. Тесты используют случайные отдельные схемы и удаляют только созданные ими схемы. После проверки очистите временные переменные окружения своего терминала.

## 6. Новый закон и новые поля

```text
официальный источник
→ staging
→ immutable snapshot с текстом, датами и происхождением
→ точные серверные сегменты
→ GigaChat extraction
→ определения фактов и ссылки на сегменты
→ детерминированные проверки
→ automatic publication либо human review
→ неизменяемая версия правила
→ персональный расчёт
→ типизированные вопросы
→ ответ пользователя
→ транзакционный пересчёт без GigaChat
```

Факты хранятся через `business_fact_definitions`, `business_fact_observations`, `company_fact_current`, `rule_fact_dependencies`. Для нового признака не нужна новая колонка профиля. Поддерживаются boolean, enum, multi_enum, number, date, text, string_list.

`unknown`, `false`, ноль и пустой список различаются. Данные могут относиться к компании или конкретной торговой точке, иметь период и срок актуальности. Если сначала нужно определить торговую точку, вопрос о ней задаётся раньше вопроса о её показателях.

`POST /impacts/:id/answers` сохраняет ответы идемпотентно. Отвечать можно на нужные этой карточке поля; `edit:true` разрешает исправлять ранее известные факты только из зависимостей этого правила. Чужие компании и произвольные поля не допускаются.

Если ответ меняет версию агрегированного профиля, пересчитываются все выбранные правила компании. Это устраняет исчезновение несвязанных карточек. Если меняется только динамический факт, пересчитываются его зависимости.

## 7. Источники и обработка ошибок

Существующие источники сохранены: `publication.pravo.gov.ru`, `government.ru`, `nalog.gov.ru`, `cbr.ru`, специализированная страница ЦБ и Роспотребнадзор. Ошибка одного источника не должна удалять проверенные правила или ломать все остальные источники.

Транспорт контролирует таймаут всего ответа, размер тела, ограниченное число попыток и перенаправления только на разрешённые официальные HTTPS-хосты. Учитываются объявленные текстовые кодировки. Исправлена обработка некорректных дат и HTML-сущностей.

Поддерживаются HTML, plain text и PDF **с текстовым слоем**. Для PDF используется `pdftotext`; у скана без читаемого текста будет явная ошибка. OCR и «восстановление закона по догадке» отсутствуют. Ограничения: загрузка до 20 MiB; PDF-текст до 120 000 символов; извлечение PDF до 20 секунд. Слишком большой текст не обрезается молча.

Номер, орган и дата публикации сохраняются в снимке, когда доступны в исходных серверных метаданных. Дата акта из заголовка не выдаётся за дату публикации. Для старых снимков неизвестные значения остаются неизвестными. Источник без даты публикации не становится «новым» только из-за будущей даты вступления в силу.

Отдельная административная повторная попытка:

```text
POST /admin/extraction-jobs/:id/retry
X-Admin-Token: значение из локального окружения
```

Она сбрасывает попытки терминально ошибочного задания без удаления источника и истории. Производственные секреты в логах ошибок не нужны.

Реальная доступность сайтов и качество нового extraction на GigaChat этой сборкой здесь не проверены. Сложные поправки со ссылками на другие акты могут требовать ручного review. Наличие серверной цитаты гарантирует происхождение цитаты, но само по себе не доказывает юридическую правильность вывода.

## 9. Архитектура и данные

- `apps/web`: mini-app и отдельный `/review`.
- `apps/api`: MAX-auth, API профиля, карточек, фактов, действий, checklist и administration.
- `apps/bot`: webhook, вход и ссылки из MAX.
- `apps/worker`: ingestion, extraction, очереди публикации, пересчёт, уведомления.
- `packages/domain`: схемы и детерминированные расчёты; отдельно читаемые тексты.
- `packages/db`: транзакции, версии, очереди, наблюдения фактов, история.
- `packages/llm`: адаптеры и grounded extraction.
- `packages/ingestion`: загрузка и разбор источников.
- `packages/review`: human review и automatic gates.

Новые пользовательские методы: `GET /company/checks`, `POST /company/checks/answer`. Ответы сохраняются в `business_check_answers`, защищённой от изменения/удаления истории. Отметка наличия документа не меняет автоматически юридическую применимость и не закрывает действия за пользователя.

`seed/v1` в 0.9.14 расширен до **37 требований**: исходные Core-7 сохранены, добавлено 30 новых правил для персональных данных, дистанционной торговли/защиты потребителей, ККТ и УСН/НДС. Для каждого нового правила есть applicability, `applies`/`not_applicable`/`needs_info` fixture, конкретные actions, evidence URL на официальный источник и dynamic facts там, где данных базового onboarding недостаточно. Seed-loader теперь устанавливает fact definitions и rule dependencies до регистрации правил, поэтому чистая база не должна упираться в отсутствующий dynamic-fact registry. Подробная карта источников и ограничения — `LEGAL_SEED_RESEARCH_0.9.14.md`. Полнота законодательства не заявляется.

## 10. Проверка в настоящем MAX

0.9.15 использует одного бота и как канал уведомлений, и как быстрый интерфейс к Mini App. После деплоя выполнить `npm run bot:subscribe` внутри bot-контейнера: команда синхронизирует webhook и список slash-команд MAX.

Чат поддерживает `/start`, `/menu`, `/status`, `/requirements`, `/actions`, `/changes`, `/documents`, `/history`, `/profile`, `/help`, а также эквивалентные обычные русские фразы. Свободный тематический запрос ищет только среди уже рассчитанных персональных требований; если уверенного совпадения нет, бот не выдумывает юридический ответ и возвращает пользователя в структурированное меню. В групповых чатах персональные результаты не раскрываются.

`/actions` позволяет открыть точную карточку Mini App и после отдельного подтверждения отметить актуальный action выполненным прямо из callback-кнопки. Native `open_app` передаёт `start_param`, а frontend 0.9.15 понимает `assessment_<impactId>`, `profile`, `feed`, `documents`, `history`, `check/home/actions` и открывает нужный экран после MAX-auth.

Обязательный live-проход после выкладки: `/start` → меню → статус → требования → тематический поиск → действия → подтверждение action → проверка статуса в Mini App → изменения → документы → история → профиль → help; отдельно проверить незаполненный профиль, устаревшую action-кнопку, stop/resume бота, notification deep-link и mobile/web MAX. Полная матрица: `BOT_SCENARIOS_0.9.15.md`.

`S*_VALIDATION.md` и `docs/history/README_0.9.9.md` являются историческими материалами. Их старые результаты не подтверждают новую сборку. `SOURCE_MANIFEST.sha256` сформирован для файлов текущего архива, кроме `.env`, самого manifest и временных/генерируемых данных.

Проверка контрольных сумм исходников:

```powershell
node scripts/verify-manifest.mjs
```
