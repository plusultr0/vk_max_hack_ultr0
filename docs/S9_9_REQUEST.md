Продолжаем разработку текущего проекта MAX Regulatory Control. Используй **последний загруженный ZIP проекта как единственную актуальную базовую версию исходников** и весь контекст текущего чата. Не начинай проект заново.

Текущие S9.4–S9.8 уже реализованы в этой версии: grounded extraction, source snapshots, human review/revisions, atomic publication, outbox, background company reassessment, lifecycle/versioning, action carry-over, background extraction jobs и техническая MAX-цепочка. Твоя задача — расширить текущую архитектуру новым этапом:

# S9.9 — Autonomous Regulatory Engine

## Главная продуктовая цель

Предприниматель не должен самостоятельно отслеживать выход новых законов и разбираться, относятся ли они к его бизнесу.

Пользователь:

1.  при первом входе заполняет минимальный профиль бизнеса; 
2.  дальше система самостоятельно отслеживает нормативные изменения; 
3.  определяет потенциально затрагиваемый сегмент компаний; 
4.  проверяет применимость к конкретному бизнесу; 
5.  если данных не хватает — спрашивает их прямо внутри карточки; 
6.  если данные устарели — просит только подтвердить или изменить их; 
7.  после ответа автоматически пересчитывает применимость; 
8.  показывает предпринимателю только итог: 
   -  касается; 
   -  возможно касается, нужны данные; 
   -  не касается; 
   -  скоро вступит в силу; 
   -  что конкретно необходимо сделать; 
   -  до какого срока; 
   -  почему система так решила; 
   -  официальный источник/evidence. 

Помимо новых изменений система должна уметь проверять **действующие старые нормативные требования**, которые могли появиться до регистрации пользователя.

---

# 1. Business Fact Registry

Реализуй универсальный реестр признаков бизнеса.

Новые признаки НЕ должны требовать новой PostgreSQL-колонки и изменения формы вручную.

Fact Definition должен как минимум поддерживать:

-  stable key; 
-  human title; 
-  description; 
-  value type; 
-  scope (`company`, `trade_object` и расширяемые варианты); 
-  question text; 
-  UI input type; 
-  enum/options при необходимости; 
-  freshness policy; 
-  periodic/non-periodic semantics; 
-  validation metadata; 
-  creation origin; 
-  timestamps/versioning при необходимости. 

Значение факта для компании должно хранить:

-  fact definition; 
-  company/scope target; 
-  value; 
-  source; 
-  confirmedAt; 
-  applicable period, если показатель периодический; 
-  provenance/audit. 

Существующие profile fields нужно интегрировать с этой моделью максимально обратно совместимо. Не ломай текущий profile/evaluator.

---

# 2. Dynamic Fact Creation

При extraction нового нормативного правила система должна определять:

-  какие бизнес-факты необходимы для applicability; 
-  какие уже существуют; 
-  каких нет. 

Если факта нет, LLM может предложить **декларативное Fact Definition**:

-  key; 
-  type; 
-  scope; 
-  question; 
-  options; 
-  semantic description. 

Это не должно требовать обязательного admin approval.

Перед автоматическим созданием обязательно проходят deterministic quality gates:

-  разрешённый type; 
-  корректный key namespace; 
-  корректный scope; 
-  отсутствие семантического/ключевого дубликата; 
-  корректные options; 
-  отсутствие executable code; 
-  успешная schema validation; 
-  возможность безопасно использовать факт в DSL. 

Если автоматическая проверка не уверена или есть конфликт — отправить rule/fact во внутренний `needs_review`.

---

# 3. Fact Freshness

Реализуй актуальность бизнес-фактов.

Нужны состояния примерно:

- `fresh`; 
- `stale`; 
- `missing`. 

Различай:

-  практически неизменяемые facts; 
-  изменяемые facts; 
-  периодические показатели; 
-  событийные facts. 

Пример:

`tax.regime`

может требовать подтверждения примерно раз в месяц.

Если значение ещё актуально — повторно не спрашивать.

Если устарело и требуется новому правилу:

показать пользователю:

«У вас по-прежнему УСН — доходы минус расходы?»

`Да, всё верно / Изменить`

Один ответ обновляет факт для ВСЕХ правил, которым он нужен.

---

# 4. Periodic Facts

Выручку, employee count и другие периодические показатели нельзя хранить одним глобальным значением.

Поддержать значения с периодами:

-  month; 
-  quarter; 
-  calendar year; 
-  current YTD; 
-  при необходимости explicit date range. 

Rule должен запрашивать конкретный semantic period, например:

`revenue.previous_calendar_year`

и evaluator обязан брать соответствующее значение.

---

# 5. Rule Required Facts

Каждое новое правило должно явно хранить список/структуру facts, необходимых:

-  для targeting; 
-  для полного applicability; 
-  для compliance assessment; 

чтобы система понимала, какие данные потребуются предпринимателю.

---

# 6. Coarse Targeting / Company Cohorts

При публикации закона НЕ запускай тупой full scan всех компаний.

Реализуй дешёвый targeting layer на индексируемых признаках:

-  legal form; 
-  region; 
-  OKVED/business category; 
-  B2B/B2C; 
-  tax regime; 
-  company size; 
-  sales channel; 
-  другие безопасные prefilter facts. 

Пример:

1 000 000 компаний

→ ИП/ООО

→ B2C

→ e-commerce

→ USN

→ только этот cohort идёт в полный evaluator.

Физически отдельные БД для ИП/ООО создавать не нужно. Используй одну модель данных + индексы/cohorts/materialized targeting, если это необходимо.

Targeting НЕ является окончательным юридическим verdict.

---

# 7. Applicability States

Расширь текущую механику так, чтобы результат мог различать:

- `APPLIES`; 
- `NOT_APPLICABLE`; 
- `NEEDS_INFO`; 
- `NEEDS_CONFIRMATION`. 

`NEEDS_INFO` = значения никогда не было.

`NEEDS_CONFIRMATION` = значение известно, но его freshness недостаточна для этого правила.

Не ломай существующую tri-state модель; интегрируй это обратно совместимо.

---

# 8. Dynamic Questions Inside Impact Card

Если правило потенциально относится к бизнесу, но не хватает данных, карточка пользователя должна показывать:

«Возможно, касается вашего бизнеса».

Затем автоматически сгенерированные типизированные поля:

-  boolean; 
-  select; 
-  multi-select; 
-  number; 
-  date; 
-  text; 
-  при необходимости другие безопасные declarative input types. 

Пример:

`Ваш налоговый режим`

`[УСН — доходы минус расходы ▼]`

`Выручка за 2025 год`

`[____________ ₽]`

Кнопка:

`Проверить применимость`

После submit:

-  сохранить facts; 
-  создать корректную новую profile/fact version/audit trail; 
-  не вызывать GigaChat; 
-  запустить deterministic evaluator только для необходимых rule/company; 
-  обновить impact. 

Если результат `NOT_APPLICABLE`, показать понятную карточку:

«По указанным данным это изменение не требует от вашей компании действий»

плюс объяснение почему.

Если `APPLIES` — показать стандартный action plan.

---

# 9. GigaChat Boundary

Очень важно:

GigaChat используется на уровне НОРМАТИВНОГО ДОКУМЕНТА.

Не отправляй каждого пользователя или каждый новый ответ пользователя в GigaChat.

Целевая схема:

`law -> GigaChat once -> structured validated rule -> deterministic evaluator many times`

а не:

`law × every company -> GigaChat`.

---

# 10. Automatic Rule Publication

Текущий обязательный human review нужно перестроить.

Human review НЕ должен оставаться обязательным bottleneck для каждого закона.

Реализуй:

`extraction -> deterministic quality gates -> AUTO_PUBLISH or NEEDS_REVIEW`

Auto-publish разрешён только если проходят все необходимые проверки:

-  источник доверенный/официальный; 
-  snapshot сохранён; 
-  grounded evidence корректен; 
-  все source segment refs существуют; 
-  dates/temporal phases валидны; 
-  operators/types валидны; 
-  required facts существуют или безопасно созданы; 
-  DSL успешно компилируется; 
-  нет известных логических конфликтов; 
-  publication сохраняет immutable/versioning guarantees. 

Если хотя бы один safety gate не проходит:

`NEEDS_REVIEW`

и используется уже существующая human-review инфраструктура.

Не удаляй human-review систему — она становится fallback.

---

# 11. Regulatory Feed

Добавь пользовательскую ленту нормативных изменений.

Это НЕ общий поток всех российских законов.

Пользователь должен видеть релевантные/потенциально релевантные ему события.

Категории примерно:

-  новые; 
-  может касаться вас; 
-  требуют действий; 
-  предстоящие; 
-  проверенные; 
-  не относятся. 

Сохраняй дату публикации/обнаружения/вступления в силу отдельно.

---

# 12. Historical Compliance Baseline

Новый пользователь должен проверяться не только против законов, вышедших после регистрации.

Реализуй baseline текущих действующих норм.

На onboarding/profile confirmation:

`все действующие rules`

→ cheap targeting

→ candidate set

→ deterministic evaluation

В результате пользователь может увидеть действующую обязанность, которая появилась год, три или десять лет назад, если она всё ещё действует и относится к его бизнесу.

Не создавать пользователю карточку только потому, что акт исторически существовал: учитывать текущий `validFrom / validTo / cancellation/version lifecycle`.

---

# 13. User Product Structure

Пока не делай большой redesign.

Но технически подготовь/добавь необходимые экраны и API:

### Главная

-  Требуют действий; 
-  Нужно уточнить; 
-  Скоро вступят в силу; 
-  Всё проверено / состояние. 

### Изменения

Персонализированная нормативная лента.

### Проверка бизнеса

-  требуют действий; 
-  нужно уточнить; 
-  рекомендуем проверить; 
-  выполнено; 
-  история.

# 14. Required end-to-end acceptance scenario

В конце обязательно должен проходить сценарий:

1.  появляется новое официальное нормативное изменение; 
2.  ingestion его сохраняет; 
3.  GigaChat извлекает структуру; 
4.  в правиле присутствует ранее неизвестный business fact; 
5.  система автоматически создаёт safe Fact Definition; 
6.  automated gates успешно публикуют rule; 
7.  targeting выбирает только потенциально затронутый cohort; 
8.  часть компаний получает `NOT_APPLICABLE`; 
9.  часть получает `APPLIES`; 
10.  часть получает `NEEDS_INFO`; 
11.  пользователь видит новый вопрос прямо в карточке; 
12.  отвечает; 
13.  GigaChat повторно НЕ вызывается; 
14.  fact сохраняется; 
15.  deterministic evaluator пересчитывает rule; 
16.  карточка превращается в `APPLIES` либо `NOT_APPLICABLE`; 
17.  applicable case получает action plan; 
18.  ответ пользователя становится доступен другим правилам; 
19.  stale fact позднее вызывает `NEEDS_CONFIRMATION`, а не новый полный ввод; 
20.  новый пользователь также получает baseline по старым действующим правилам.

Работай последовательно:

`S9.9.1 Business Fact Registry`

`S9.9.2 Dynamic Fact Definitions`

`S9.9.3 Fact freshness + periodic values`

`S9.9.4 Rule requiredFacts + targeting predicates`

`S9.9.5 Indexed/cohort targeting + targeted reassessment`

`S9.9.6 NEEDS_INFO / NEEDS_CONFIRMATION + dynamic question API`

`S9.9.7 Inline questions + Проверить применимость`

`S9.9.8 Automatic quality gates + auto-publish/fallback`

`S9.9.9 Regulatory feed`

`S9.9.10 Historical Compliance Baseline`

`S9.9.11 Full regression + end-to-end`

Это один общий запрос, но НЕ делай один гигантский непроверенный rewrite. После каждого подэтапа:

-  typecheck; 
-  relevant unit tests; 
-  integration tests; 
-  migrations; 
-  backward compatibility checks. 

Если ошибка появилась — исправь её до перехода дальше.

Не спрашивай у меня подтверждение между S9.9.x этапами. Продолжай самостоятельно, пока не встретишь реальный blocker, который невозможно решить по коду/контексту.

# КАТЕГОРИЧЕСКИ НЕЛЬЗЯ

-  не начинать проект заново; 
-  не делать отдельную новую архитектуру рядом со старой; 
-  не ломать S9.4–S9.8; 
-  не хардкодить dynamic facts PostgreSQL-колонками; 
-  не давать LLM генерировать или исполнять SQL/JS/TS; 
-  не использовать LLM как final applicability evaluator; 
-  не делать GigaChat-запрос на каждую компанию; 
-  не делать full scan всех компаний без targeting; 
-  не возвращать обязательный ручной review для каждого правила; 
-  не auto-publish невалидный/ungrounded rule; 
-  не считать unknown=false; 
-  не считать applies=violation; 
-  не использовать stale fact как fresh; 
-  не спрашивать одинаковый актуальный факт повторно; 
-  не хранить периодические metrics без периода; 
-  не удалять историю профилей/rules/assessments/actions; 
-  не ломать semantic completed-action carry-over; 
-  не делать большой UI redesign; 
-  не ограничивать архитектуру текущими core-7; 
-  не превращать feed в общий поток нерелевантных законов; 
-  не учитывать только законы после регистрации пользователя; 
-  не удалять `.env`; 
-  не переписывать `.env`; 
-  не ротировать текущие secrets; 
-  не выводить секреты в ответы/логи; 
-  не удалять PostgreSQL volume; 
-  не использовать `docker compose down -v`. 

`.env` внутри последнего ZIP находится там **намеренно**. Это актуальный рабочий env для разработки на разных устройствах. Используй его как текущий конфиг и не меняй без технической необходимости. Перед финальной публикацией проекта секреты будут очищены отдельно.
