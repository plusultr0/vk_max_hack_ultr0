# MAX Regulatory Control — технический разбор

Дата: 17.09.2026. Основание: предоставленные ZIP и файл контекста, чтение исходников, локальные тесты, сборка и один успешный live smoke GigaChat на синтетическом тексте.

## Что разрабатываем

Мини-приложение MAX для регуляторного контроля малого e-commerce. Главный сценарий: изменение в официальном источнике → проверенный человеком нормативный черновик → применимость к компании → действия и сроки → уведомление и переход из MAX.

GigaChat извлекает структуру. Решение о применимости принимает детерминированный движок. «Относится к компании» не означает «компания нарушает требование». Неизвестный ответ не равен отрицательному. Версии правил, оценок и история выполнения должны сохраняться.

Предписания из приложенного контекста использованы как описание прошлых решений и планов. Отдельной команды автоматически выполнить все перечисленные там этапы пользователь не давал. На этом шаге выполнены аудит, проверки и небольшое исправление теста.

## Какая копия актуальна

В ZIP две самостоятельные копии:

- `project/` — более ранняя реализация.
- `max-regulatory-control-through-s9/project/` — версия 0.9.3, с multi-source ingestion, GigaChat, сертификатом и `.env`. Именно она проверена.

## Основные технические находки

### 1. S9.4 требует неизменяемого снимка источника

`packages/db/src/ingestion.ts:65` перезаписывает `source_documents.raw` при обновлении источника. Candidate хранит ссылку на документ, draft и цитаты, но не точный полный текст, использованный для extraction. `apps/api/src/index.ts:425` допускает текст из тела запроса; его происхождение возвращается клиенту, но не сохраняется с candidate. Текст, заново полученный по URL, также не сохраняется как отдельный снимок extraction.

Предлагаю сохранять вместе с extraction неизменяемый текст, его SHA-256, URL, происхождение, время получения и версию алгоритма сегментации. Индексы сегментов должны относиться к этому снимку. Иначе после обновления страницы проверяющий не сможет надёжно восстановить исходное основание черновика.

### 2. Проверка цитат не проверяет смысл полей

В `packages/llm/src/index.ts` сроки — произвольные строки. В успешном live smoke получено `actionDrafts[0].deadlineHint = "date_eq"`: оператор вместо срока. Текущий quality gate это пропустил. Это результат на синтетическом тестовом тексте, а не юридический вывод.

Предлагаю типизированный срок: фиксированная дата / относительный срок / неизвестно, с отдельными ссылками на источник. Дословная цитата доказывает происхождение текста, но сама по себе не доказывает, что условие, дата или действие правильно из него выведены. Проверка человеком остаётся обязательной частью workflow.

### 3. Repair не охватывает ошибки схемы

`packages/llm/src/index.ts:189` вызывает `RegulatoryExtractionSchema.parse(firstRaw)` до ветки repair. Например, пустой обязательный массив evidenceIndexes или неправильный operatorHint завершит extraction сразу. Одна попытка исправления предусмотрена для ошибок ссылок/цитат, но не для всех невалидных ответов.

Предлагаю общий сбор ошибок схемы и grounding, одну ограниченную repair-попытку и запрет сохранения при повторном провале. Сетевые ошибки должны иметь отдельную политику, чтобы не маскировать их как ошибку юридической структуры.

### 4. Поэтапные нормы пока не представлены структурно

Prompt в `packages/llm/src/index.ts:132` прямо требует извлечь самый ранний этап, а последующие поместить в `uncertaintyNotes`. Это сохраняет их лишь как свободный текст, непригодный для исполнения движком. Полнота перечня этапов не проверяется.

Варианты: расширить domain модель фазами или создавать отдельные правила для этапов одного акта. Для ближайшего MVP предлагаю структурированный список фаз в draft и отдельные ruleId для утверждённых фаз. Версии одного ruleId использовать для исправлений/изменений соответствующего правила: текущий выбор последней версии не позволит одновременно исполнять несколько фаз как независимые версии. До реализации нельзя считать этапы из uncertaintyNotes полноценными правилами.

### 5. Публикация может завершиться без полного пересчёта

В `packages/db/src/ingestion.ts:197` происходит COMMIT публикации, а на строке 203 начинается пересчёт компаний. При сбое правило уже опубликовано, но часть компаний может остаться без новых результатов. Повторный publish отклоняется как `CANDIDATE_ALREADY_REVIEWED`.

Предлагаю в транзакции публикации создавать долговечное задание пересчёта, а worker должен выполнять его с повторными попытками. Нужны статус выполнения и идемпотентность. Аналогично следует проверить создание уведомлений после сохранения assessment: ранний возврат для существующей оценки может пропустить восстановление побочного действия после сбоя.

### 6. Активный список смешивает версии; отмена требует отдельной проверки

`packages/db/src/impacts.ts:141` фильтрует impacts по текущей версии профиля, но не выбирает последнюю оценку правила. После публикации новой версии старый и новый impacts могут одновременно попасть в основной список.

Также `getCurrentRules()` сначала исключает `repealed/expired`, а затем выбирает последнюю версию. Если новая версия отменена, более старая active-версия может снова попасть в выборку. Предлагаю сначала выбирать нужную последнюю утверждённую версию с учётом модели действия во времени, затем интерпретировать её статус. Историю показывать отдельно от текущих задач.

### 7. Уже поставленные напоминания могут устареть

`updateActionStatus()` не отменяет существующее напоминание при завершении задачи; `claimDueNotification()` и отправка не проверяют актуальный статус действия. Напоминание, созданное до выполнения или пересмотра действия, может уйти позднее.

Предлагаю отменять неподходящие pending/retry уведомления и повторно проверять актуальность непосредственно перед отправкой. Учитывать completed/dismissed, review_required и активность получателя. Это вывод по коду; сценарий ещё не воспроизведён с БД и MAX.

### 8. Human review реализован как API, интерфейса редактора нет

Есть endpoints списка candidates, reject и publish. Publish принимает вручную подготовленный `LegalRule`, а не предоставляет законченный процесс редактирования draft. В React-приложении нет административного экрана candidate/источник/редактор/подтверждение.

Предлагаю минимальный отдельный экран: источник и сегменты рядом с черновиком, редактирование условий/сроков/действий, пробный расчёт на профилях, список ошибок, подтверждение новой версии. Перед publish нужно проверять привязку к снимку и допустимость перехода статуса. Сейчас reject может менять статус уже approved candidate, поскольку SQL не ограничен состоянием pending.

### 9. Сборка пока не воспроизводима по зависимостям

В предоставленных копиях нет package-lock.json, Dockerfile вызывает `npm install`. При проверке lockfile создан только в рабочей копии; он не является уже согласованным lockfile проекта.

Предлагаю отдельно зафиксировать проверенный lockfile и перейти на `npm ci`, затем повторить чистую контейнерную сборку. Для внешнего MAX-сценария понадобятся доступные HTTPS-адреса, конфигурация production и фактическая проверка авторизации, webhook и deep-link. Текущий compose запускает Vite dev server.

## Предлагаемый порядок разработки

1. S9.4: неизменяемый снимок → точные сегменты → ссылки модели → серверные цитаты; общий quality gate и bounded repair; типизация сроков и структурные фазы.
2. Минимальный human review с проверяемым преобразованием draft в domain rule.
3. Надёжный publish/reassessment, выбор текущих версий, отмена устаревших напоминаний, интеграционные тесты отказов и повторов.
4. Live MAX: реальные настройки, HTTPS, вход, webhook, уведомление, переход на конкретную карточку.
5. Воспроизводимый запуск и демонстрация: lockfile, контейнерная проверка, README, фиксированный commit и end-to-end сценарий.

Критерий готовности S9.4: модель не управляет сохранённой цитатой; каждый индекс проверен в конкретном снимке; при смене страницы старые доказательства восстанавливаются; невалидный ответ после repair не сохраняется; последующие фазы не исчезают; live extraction официального документа проверен целиком. До этого называть S9.4 реализованным нельзя.
