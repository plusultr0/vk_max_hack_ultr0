# S9.5A/B — серверная основа проверки человеком

Версия 0.9.5, 17.09.2026. Следующий блок после S9.4. Пользовательский интерфейс не изменён.

## Что добавлено

- Пакет `@reg/review`: структура проверяемого документа, серверное создание черновика, компилятор в domain DSL, чистый предпросмотр.
- Миграция 008: `review_drafts` связывает candidate с исходным snapshot и текущей ревизией; `review_revisions` хранит неизменяемые ревизии, состояние, автора, причину, SHA-256 содержимого и результат компиляции.
- Транзакционная запись ревизии, указателя текущей ревизии и аудита. Оптимистическая блокировка по `baseRevision`, сериализация по candidate.
- API создания, чтения, истории, сохранения и предпросмотра. Старый endpoint публикации отказывает кандидату, для которого начат новый review.
- Отклонение разрешено только из pending; терминальный статус candidate защищён также триггером PostgreSQL.

Исходное извлечение и snapshot остаются неизменными. В проверяемом документе сохраняется отдельный UUID каждого этапа/условия/исключения/действия и его originIndex в исходном извлечении. Перестановка элементов разрешена; удаление ранее сохранённого элемента или переназначение его происхождения запрещено. Для исключения используется decision=exclude с причиной. Новые элементы создаются с новым UUID и originIndex=null.

У разных одновременно действующих этапов разные ruleId. Номер version относится к редакции отдельного правила. Связь с существующими опубликованными версиями, допустимость следующего номера и коллизии ruleId будут проверяться в новом механизме публикации; текущий компилятор ничего не публикует.

## Проверки компилятора

Каждый элемент требует include/exclude и обоснование. Неопределённый элемент блокирует готовность пакета. Исключение всего этапа с причиной покрывает его содержимое; этап нельзя просто удалить.

Условие поддерживает вложенные AND/OR/NOT. Для каждой конечной проверки задаются поле, оператор, значение, область применения и сегменты. Поддерживаются eq/neq, gt/gte/lt/lte, in, contains_any/all, known, is_empty. Типы и enum проверяются по CompanyProfileSchema; сравнения массивов через eq запрещены. `exists` из AI-извлечения намеренно не конвертируется автоматически: заполненность поля не доказывает наличие договора.

Применимость строится как выбранная AND/OR-связка условий AND NOT(OR исключений). Отсутствующие сведения компании дают needs_info через существующий tri-state evaluator. Неопределённая структура самого правила блокирует компиляцию и не маскируется под needs_info.

Сегменты и цитаты берутся из сохранённого снимка. Даты должны присутствовать в процитированных сегментах. Для каждого используемого поля нужен questionMap; вопросы по неиспользуемым полям отклоняются. Все исходные uncertaintyNotes, dateNotes и reviewWarnings требуют явного решения с пояснением. Проверяющий отдельно подтверждает полноту чтения источника и правовое основание. Эти подтверждения не являются автоматической юридической проверкой.

Проверки торговой точки допускаются только для этапа scope=trade_object. Поля компании можно использовать как контекст этого этапа. Предпросмотр точки требует явного tradeObjectId и данных именно этой точки. Хранение нескольких точек компании и их боевой пересчёт пока не реализованы: результаты такого предпросмотра нельзя автоматически применять ко всей компании.

Сроки:

- fixed — дата с подтверждением в сегментах;
- phase_start — производный срок по началу этапа, сохраняющий это происхождение в ревизии;
- none — явное решение с объяснением отсутствия срока;
- unknown/relative — блокируют готовность, пока проверяющий не разрешит вопрос поддерживаемым способом. Автоматической подмены датой начала нет.

Состояние времени в новом предпросмотре: upcoming / active / ended, границы `[validFrom, validTo)`. validTo исключена; проверяющий должен подтвердить именно такую интерпретацию границы. Включительные окончания и иные вычисляемые границы требуют расширения контракта, а не механической подстановки даты. Начало следующего этапа не создаёт конец предыдущего. Отсутствие конца тоже требует объяснения.

Компилятор возвращает либо весь пакет, либо пустой `rules` и список блокирующих issues. Предложения правил имеют reviewStatus=needs_review и метку review-preview. `ready` означает готовность структуры к следующему процессу проверки/публикации; candidate при этом остаётся pending.

## API

Все маршруты требуют `X-Admin-Token`. Текущий способ аутентификации определяет одного общего субъекта `admin-token`; он не доказывает личность конкретного сотрудника. Произвольный actorId из тела запроса не принимается. Персональные роли и авторизация редактора — следующий блок.

| Метод и путь | Результат |
|---|---|
| POST `/admin/candidates/:id/review` с `{}` | Ревизия 1, draft, HTTP 201 |
| GET `/admin/candidates/:id/review` | Текущая ревизия и результат компиляции |
| GET `/admin/candidates/:id/review?revision=1` | Конкретная историческая ревизия |
| GET `/admin/candidates/:id/review/history` | Номера, состояния, хеши, авторы и причины ревизий |
| PUT `/admin/candidates/:id/review` | Новая неизменяемая ревизия |
| POST `/admin/candidates/:id/review/preview` | Гипотетический расчёт без записи assessments/actions |

Тело сохранения:

```json
{
  "baseRevision": 1,
  "state": "draft",
  "reason": "Уточнено условие договора по исходному сегменту",
  "document": "полный объект document, полученный при чтении, с правками"
}
```

В реальном запросе `document` — объект, а не строка из поясняющего примера. Для перехода в ready все блокирующие issues должны быть устранены. Из ready можно создать новую draft-ревизию; старое решение останется в истории.

Тело предпросмотра:

```json
{
  "revision": 2,
  "contentHash": "SHA-256 из ответа сохранения",
  "asOf": "2026-09-17",
  "profile": { "profileVersion": 1 }
}
```

Для scope=trade_object добавляется `tradeObjectId`. Профиль в запросе является гипотетическим, не обновляет профиль компании и не позволяет получить доступ к чужим сохранённым карточкам. Предпросмотр возвращает номер и хеш конкретной ревизии. Изменение текущей ревизии или неверный хеш даёт 409. Если правка происходит одновременно после чтения ревизии для preview, ответ всё равно привязан к прочитанному номеру/хешу и не означает одобрение следующей ревизии.

Ответы: 400 — неверный формат; 403 — нет admin-доступа; 404 — запись не найдена; 409 — конфликт ревизии/терминальный candidate/повтор создания; 422 — недопустимое происхождение или неготовый пакет. Неожиданные ошибки БД остаются серверными ошибками.

## Обновление и запуск

В каталоге проекта сохранить существующий `.env` и PostgreSQL volume. Для этой локальной установки имя Compose-проекта — `max-regcontrol-s94`; оно сохранено для использования прежнего тома, несмотря на новую версию кода.

```powershell
docker compose -p max-regcontrol-s94 up -d --build
docker compose -p max-regcontrol-s94 run --rm --no-deps api npm run check
docker compose -p max-regcontrol-s94 run --rm --no-deps -e ALLOW_INTEGRATION_TESTS=true api npm run test:integration
```

На другой существующей установке использовать её прежнее имя Compose-проекта. Не выполнять `down -v`, если нужно сохранить данные. На чистой установке миграции и seed запускаются зависимостями Compose. Архив содержит исходники, а не снимок рабочей БД.

Интеграционные тесты создают случайную отдельную схему, дважды применяют миграции, запускают временный HTTP API на свободном локальном порту и удаляют только собственную схему. Внешние MAX/LLM-запросы в этих тестах не выполняются.

## Границы этого блока и следующий шаг

1. Добавить минимальный UI редактора: source рядом с полями, переходы к цитатам, issues, решения, сохранение и история, гипотетические профили.
2. Реализовать публикацию проверенной ревизии целым пакетом, проверку существующих ruleId/version и транзакционный outbox для пересчёта. Старый одноэтапный publish остаётся legacy-путём для кандидатов без нового review и не заменяет новый процесс.
3. Перенести политику времени и областей применения в боевой выбор правил/пересчёт; исправить отмену и текущую выдачу impacts. Чистый preview этого блока не меняет существующий `getCurrentRules()`.
4. Доработать сохранение выполненных действий, напоминания, затем полный MAX-сценарий.

Сохранённый кандидат ЦБ не исправлен «за человека», не переведён в ready и не опубликован. Его regression fixture подтверждает сохранение трёх этапов и блокировку известных проблем, а не правильность юридического вывода. Полнота DSL проверена на явно синтетических примерах.
