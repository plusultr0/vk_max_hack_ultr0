# S9.9 — Autonomous Regulatory Engine: реализация

Версия проекта: **0.9.9**. Базовая версия исходников: `vk_max_hack_ultr0-main (1).zip`.
Этот файл описывает внесённый код. Фактически выполненные проверки и ограничения среды — в `S9_9_VALIDATION.md`.

## Статус

S9.9 внесён в существующий проект, без создания отдельного приложения. Добавлены реестр фактов, периодизация и подтверждения, таргетированный пересчёт, автоматический путь публикации, вопросы в карточке, лента и проверка действующих требований.

**Это сборка для локальной приёмки. Полная приёмка S9.9 ещё не завершена:** миграции на PostgreSQL, обычный TypeScript typecheck, Vitest, Vite и настоящий GigaChat/MAX в этой среде не выполнены. Успешный автоматический разбор произвольного нового закона не гарантируется.

## 1. Реестр и наблюдения фактов

Новые файлы `packages/domain/src/fact-schema.ts`, `fact-logic.ts`, `fact-builtins.ts`; хранилище — `packages/db/src/facts.ts`.

`business_fact_definitions` содержит версионируемое определение: key, semanticKey, type, title, description, question, options, scope, unit, validation bounds, freshness, periodic, origin. Факты не создают колонки БД. Введены типы boolean, enum, multi_enum, number, date, text, string_list.

`business_fact_observations` хранит неизменяемые ответы: company, scope target, key/version, value, period, confirmedAt, source, provenance. `company_fact_current` — индексируемая текущая проекция поверх истории. Существующие profile fields импортируются через builtin-определения, а не удаляются.

Импорт использует исходную дату подтверждения каждого изменённого поля. Ответ на другой вопрос не обновляет актуальность всего профиля. История профилей, правил, оценок и действий сохранена.

Определения и значения разделены. Набор допустимых scope сейчас ограничен `company` и `trade_object`; новые виды контекста требуют явного расширения движка, а не исполняемого описания от модели.

## 2. Новые признаки из извлечения

Расширение extraction `automation` описывает новые определения и привязки conditions → requiredFacts. LLM видит каталог определений и официальный документ; профили компаний не передаются.

Машинный путь создаёт только новые определения версии 1 с `origin=model`, безопасными ключами и разрешёнными типами. Коллизии key/version, semanticKey, одинаковых нормализованных названий/вопросов блокируют публикацию. Не допускаются произвольные SQL, код, regex-валидаторы или исполняемые выражения.

**Проверка семантических дублей ограниченная:** совпадения известных идентификаторов и нормализованного текста выявляются, но эквивалентность любых перефразировок не доказуема этим механизмом. Неоднозначные случаи должны попадать в fallback; автоматическое объединение разных смыслов не выполняется.

Оператор может исправить definition/binding в существующем review и создать следующую версию определения. Уже опубликованные правила закреплены за прежними версиями. Автоматическая ветка не меняет ранее зарегистрированную семантику.

## 3. Актуальность и периоды

Поддерживаются `fresh`, `stale`, `missing`. `false`, `0`, пустой список и `null` не смешиваются: null остаётся неизвестным значением.

Требование может задавать более строгий maxAgeDays, чем определение. Mutable builtin-факты, включая налоговый режим, имеют месячное подтверждение; исторические сведения отделены от текущих.

Периоды: month, quarter, calendar_year, previous_calendar_year, current_ytd, explicit range, as_of. Интервалы дат — полуоткрытые `[start, end)`. Конкретный год не заменяется другим годом при повторном использовании.

YTD хранится как измерение на конкретную дату. Оно может повторно использоваться в пределах политики актуальности, но остаётся именно датированным измерением. Возраст измерения и возраст подтверждения проверяются отдельно. Нажатие подтверждения не делает старую дату измерения актуальной. Для нового периода требуется отдельное наблюдение.

Ответ о налоговом режиме на прошлую дату не перезаписывает текущий налоговый режим. Периодические числовые данные зеркалируются в старые поля только при совпадении смысла периода.

## 4. Применимость и вопросы

Сохранены исходные verdict: `applies`, `not_applicable`, `needs_info`.
Отдельный `clarificationState`: `needs_info`, `needs_confirmation` либо null. Не вводится несовместимый четвёртый verdict.

Перед существующим evaluator факты разрешаются по периоду, версии, scope и актуальности. Missing/stale не становятся false. При доказанном исключении лишние вопросы подавляются. Недостающие compliance-параметры не превращаются в установленное нарушение.

`fact_context`, `calculation_key` и `next_fact_check_at` фиксируют входы расчёта. Старые assessments без информации об актуальности остаются в истории; worker создаёт новую оценку. API сообщает `refreshPending`, пока актуальный результат не готов.

В карточку добавлена пакетная типизированная форма. Пользователь может подтвердить старое значение, изменить его или указать «не знаю». Submit сохраняет ответы и пересчитывает связанные правила **без обращения к LLM**.

Запрос проверяет ownership, актуальность карточки, допустимые поля, типы и expectedObservationId. Идемпотентность привязана к company/requestId и hash тела. Один ответ переиспользуется всеми правилами, зависимыми от этого факта. Наблюдения, профильное зеркало, пересчёт и audit сохраняются в одной транзакции.

## 5. Таргетинг компаний

`compileTargeting` строит параметризованный SQL из того же applicability-выражения, которое использует evaluator. Отдельного непрозрачного LLM-классификатора аудитории нет.

Используются индексы current-проекции по key/version/period/value. AND/OR сохраняются; NOT, неподдерживаемые операции, YTD и outlet-контекст расширяют выборку, когда безопасно исключить компанию нельзя.

**Missing/stale обязательно проходят предварительный отбор.** Ранее затронутая компания также повторно проверяется, даже если новый порог её исключает: старые действия должны стать историческими.

Outbox обрабатывает выборку keyset-страницами по 500 компаний с сохранением cursor, а не загружает миллион профилей в память. Существующие durable jobs, retries и idempotency сохранены. По изменению факта используются зависимости rule_fact_dependencies.

Если правило действительно широкое либо у многих компаний нет ключевых сведений, выборка может включать всех. Это необходимое безопасное поведение. План SQL и производительность на миллионе записей здесь не измерялись; отсутствие физического sequential scan не гарантируется.

Первичная проверка одной компании переиспользует действующий механизм выбора версий и fact-aware evaluator. Отдельный оптимизированный обратный индекс «одна компания → миллионы правил» не реализован.

## 6. Автоматическая публикация и fallback

Путь worker:

```
известный официальный источник
→ bounded automatic extraction queue
→ GigaChat/DeepSeek + snapshot + server evidence
→ декларативный automation plan
→ проверка определений, bindings, дат, scopes, типов, evidence
→ existing review compiler
→ machine_validated revision
→ existing atomic publish + dependencies + outbox
→ targeted company jobs
```

Настройки добавлены с defaults, `.env` не изменён:

- `AUTO_EXTRACTION_ENABLED=true`
- `AUTONOMOUS_RULES_ENABLED=true`
- `AUTO_EXTRACTION_BATCH_SIZE=10`

Публикация сохраняет snapshot и исходный AI-draft, ревизии, immutable rules, audit и outbox. Режим `machine_validated` виден пользователю и отличается от человеческой проверки. Старый `reviewed` используется для совместимости внутренней схемы eligibility; дополнительный approvalMode не позволяет выдавать машинный результат за заключение юриста.

Проверяются доверенный HTTPS-адрес/происхождение, source refs, точные цитаты, соответствие структурированного плана исходному extraction, числа/даты, разрешённые типы и операции, простые доказуемые логические противоречия, неизменность автоматической ревизии. Перенаправление с официального HTTPS-источника на посторонний хост запрещено.

Для штатного поддерживаемого случая подтверждение администратора не нужно. Поправки, требующие другого акта, незакрытые ссылки, guidance, неоднозначные условия, неизвестный контекст и неподдерживаемые сроки уходят в `needs_review`. Существующий review сохраняется и получил редактор metadata/bindings и динамический предпросмотр.

**Границы гарантии:** точная цитата, schema и успешная компиляция не доказывают правильность юридического толкования. Модель может ошибиться в классификации текста или пропустить смысл. Эти gates не являются автоматическим юридическим заключением. Сложные междокументные поправки нельзя публиковать путём снятия проверок.

## 7. Лента и baseline

Новые API:

- `GET /regulatory/feed?filter=relevant&offset=0&limit=30`
- `GET /company/compliance`
- `POST /company/compliance/refresh`
- `GET /company/facts`
- `GET /company/facts/history`
- `POST /impacts/:id/answers`

Feed содержит только текущие персональные assessments; категории relevant/all/new/needs_info/upcoming/action_required/checked/not_applicable/verify. Даты публикации, обнаружения, добавления в систему и вступления в силу разделены. Если официальная дата публикации не была достоверно сохранена, она остаётся null, а не выдумывается.

Baseline рассматривает активные версии из имеющейся базы, включая требования, появившиеся до регистрации компании. Ended/cancelled не выдаются за действующие. Выполненная пользователем задача, применимость и юридическое соответствие остаются разными состояниями.

**Это не новая база всех законов прошлых лет.** Загружены только известные проекту нормы и материалы настроенных источников. Historical baseline работает по этой базе. Полное наполнение актуальными нормативными редакциями — отдельная работа.

UI расширен разделами «Изменения» и «Проверка бизнеса», пакетными inline-вопросами и подтверждениями. Большой redesign не выполнен. Текущая базовая анкета сохранена; новые признаки появляются по потребности.

## 8. Миграция и обратная совместимость

Добавлена `011_business_facts.sql`; исходные миграции 001–010 не изменены. Введён журнал миграций с advisory lock и распознаванием ранее выполненных этапов: старый 010 не должен повторно создавать устаревший unique index.

Миграция добавляет таблицы/колонки/индексы; удаления пользовательских данных нет. Builtin-backfill выполняется ограниченными пакетами. Проверка на реальной копии БД обязательна до использования с рабочими данными.

MAX, его credentials, подписи, webhook, очереди уведомлений и deep links не заменялись. Сохраняются проверки устаревших уведомлений и перенос completed по неизменившемуся смыслу обязанности; для dynamic rules в identity добавлены закреплённая семантика и периоды.

Рабочий `.env` сохранён побайтно. Полный ZIP содержит его намеренно и предназначен для внутреннего использования. Публиковать этот ZIP как открытый репозиторий нельзя.

## 9. Существенные ограничения этой итерации

1. Реальные PostgreSQL migration/integration, full typecheck, Vitest/Vite и внешние API требуют локального прогона.
2. Full-text ingestion по-прежнему поддерживает HTML/text; PDF/OCR и все исторические редакции автоматически не добавлены. Недоступный источник не удаляет проверенные правила.
3. Для сложных поправок необходима существующая review-ветка. Дополнительное юридическое окружение документа автоматически не достраивается.
4. Семантическая дедупликация определения — ограниченная проверка идентификаторов/нормализованного текста.
5. Не выполнен benchmark большого cohort и большой нормативной базы. Ряд read-path запросов может потребовать дальнейшей оптимизации.
6. Динамические факты сейчас редактируются через затребованные карточкой ответы и review metadata; отдельный универсальный пользовательский редактор всех фактов не создан.
7. Идентификатор торговой точки сохранён из прежней модели; управление множеством торговых точек отдельным каталогом не добавлялось.
8. Клиентские UI и настоящий mini-app MAX не проверены браузерным end-to-end.
9. Проверки закона выполняются по сообщённым данным. Реальное выполнение обязанности не подтверждается документальным аудитом.

## 10. Следующий шаг

Сначала локальная приёмка этого ZIP: clean dependencies → typecheck/unit/web build → isolated PostgreSQL S9.9 acceptance → миграция копии текущей БД → реальный extraction одного документа → проверка автоматической публикации либо корректного fallback → вопросы и ответы в браузере.

После подтверждения — настоящий MAX/HTTPS и финальный интерфейс. Исходную рабочую копию и резервную копию БД сохранить до приёмки.
